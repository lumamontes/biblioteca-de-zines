# JVM Composition Roots, Modules, Ports, and Adapters

## 1. Where concrete implementations are assembled

### Takeaway

The JVM examples split into two broad families. Spring Boot and Micronaut commonly make the application bootstrap class a very small launcher and let framework scanning assemble annotated components; explicit `@Configuration`/`@Bean` classes remain the framework-supported escape hatch when construction and implementation selection must be visible. Spring Modulith adds module-level boundaries and verification, but does not require a separate dependency-assembly folder.

### Cited Findings

- Spring Boot recommends placing the `@SpringBootApplication` main class in a root package above the rest of the code. Its package becomes the search base for component scanning and related discovery. The official example places `MyApplication.java` beside domain-named `customer` and `order` packages, each containing `Customer`, `CustomerController`, `CustomerService`, and `CustomerRepository` rather than a global `config` or `wiring` package. — [Spring Boot: Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)
- The canonical Spring Petclinic follows that convention. `PetClinicApplication` only calls `SpringApplication.run`, while the source tree is organized under `org.springframework.samples.petclinic` with `owner`, `vet`, `model`, and `system` packages. — [PetClinicApplication.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/PetClinicApplication.java); [Petclinic package tree](https://api.github.com/repos/spring-projects/spring-petclinic/contents/src/main/java/org/springframework/samples/petclinic)
- In Petclinic, the concrete persistence implementation is not manually constructed in the launcher: `OwnerRepository` is a Spring Data `JpaRepository` interface, and `OwnerController` receives it through a constructor. This is framework-generated adapter wiring plus constructor injection, not an application-visible composition root. — [OwnerRepository.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/owner/OwnerRepository.java); [OwnerController.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/owner/OwnerController.java)
- The Kotlin Petclinic variant preserves the same arrangement: `PetClinicApplication.kt` calls `runApplication`, and feature packages such as `owner`, `vet`, and `visit` sit below the application package. Its README identifies the main class and resource/configuration locations but does not describe a dedicated assembly module. — [PetClinicApplication.kt](https://github.com/spring-petclinic/spring-petclinic-kotlin/blob/main/src/main/kotlin/org/springframework/samples/petclinic/PetClinicApplication.kt); [Kotlin Petclinic README](https://github.com/spring-petclinic/spring-petclinic-kotlin)
- Micronaut Petclinic also keeps `Application.java` as a launcher calling `Micronaut.run`. Its documented source layout uses `controller`, `dto`, `model`, `repository`, `service`, `mapper`, and `system`; the README describes these as application concerns rather than ports/adapters folders. — [Application.java](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/Application.java); [Micronaut Petclinic project structure](https://github.com/micronaut-projects/micronaut-petclinic#project-structure)
- Micronaut’s service example shows implementation selection through annotations and package scanning: `StaticPetCareEmbeddingService` implements `PetCareEmbeddingService`, is annotated `@Singleton`, and is selected only for the `oracle` environment with `@Requires(env = "oracle")`. The interface is colocated in `service`, not in a separate `ports` package. — [PetCareEmbeddingService.java](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/service/PetCareEmbeddingService.java); [StaticPetCareEmbeddingService.java](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/service/StaticPetCareEmbeddingService.java)
- Spring Framework explicitly supports visible assembly through `@Configuration` classes and `@Bean` methods. The documentation defines `@Bean` as the mechanism that instantiates, configures, and initializes an object for the IoC container, and shows `AppConfig` returning `MyServiceImpl`. — [Spring Framework: Basic Concepts: @Bean and @Configuration](https://docs.spring.io/spring-framework/reference/core/beans/java/basic-concepts.html)
- Spring Modulith’s own bootstrap example still uses a small `@Modulithic @SpringBootApplication` class with `runApplication` in Kotlin or `SpringApplication.run` in Java. Module discovery and bean assembly remain framework-based; the additional responsibility is describing and verifying application-module boundaries. — [Spring Modulith: Fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html)

### Inferences

- In convention-first Spring or Micronaut applications, the practical composition root is distributed across the framework bootstrap annotation, component annotations, repository proxy generation, conditional annotations, and configuration properties. A folder named `composition`, `wiring`, or `adapters` is not necessary for assembly to exist.
- When implementation choice is a meaningful architectural decision, the official Spring mechanism makes a configuration class or configuration package the most recognizable place to look. That is a different pattern from Petclinic’s deliberately thin launcher and implicit scanning.
- A named `application` or `bootstrap` module is therefore a signal of explicit construction, not a requirement of Spring Boot, Spring Modulith, or Micronaut.

### Gaps

- The Petclinic sources inspected here do not expose a single file that constructs every application service and adapter. Claims about the complete bean graph would require examining all annotations and auto-configuration conditions, not just the launcher and representative feature package.
- The current Micronaut Petclinic README documents package names and behavior, but it does not state an architectural rule that `service` is an application layer or that `repository` is an outbound port.

## 2. How application modules, ports, and adapters are named

### Takeaway

Domain or capability names are the most consistent module names in mature Spring examples. `ports`, `adapters`, `infrastructure`, and `application` appear when the project intentionally expresses hexagonal or layered boundaries, but framework-owned examples often use `controller`, `service`, `repository`, and `system` instead. Spring Modulith formalizes package visibility and calls exposed contracts APIs or named interfaces rather than requiring `port` and `adapter` vocabulary.

### Cited Findings

- Spring Modulith defines an application module as a unit with a provided interface, internal implementation components, and required interfaces represented by bean dependencies, listened-to events, and configuration properties. By default, each direct subpackage of the main application package is an application module package. — [Spring Modulith: Fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html)
- In the default advanced arrangement, a module’s base package is its API package and subpackages are internal. The documentation uses `example.order` for the API and `example.order.internal` for implementation details. — [Spring Modulith: Advanced Application Modules](https://docs.spring.io/spring-modulith/reference/fundamentals.html#modules.advanced)
- Spring Modulith names selectively exposed contracts with `spi` in its example: `example.order.spi` is annotated as a named interface and another module may declare an allowed dependency such as `order :: spi`. This is an explicit alternative to exposing all public types in the module. — [Spring Modulith: Named Interfaces](https://docs.spring.io/spring-modulith/reference/fundamentals.html#modules.named-interfaces)
- Spring Modulith’s verification rules enforce no cycles between application modules, access through API packages rather than internal packages, and optionally only explicitly allowed module dependencies. The same documentation shows optional jMolecules hexagonal verification as an additional rule set. — [Spring Modulith: Verifying Application Module Structure](https://docs.spring.io/spring-modulith/reference/verification.html)
- Canonical Java Petclinic uses domain feature packages (`owner`, `vet`) and places controllers, repositories, entities, formatters, and validators together in those feature packages. The `owner` package contains `OwnerController`, `OwnerRepository`, `Owner`, `Pet`, `Visit`, and related types. — [Petclinic owner package tree](https://api.github.com/repos/spring-projects/spring-petclinic/contents/src/main/java/org/springframework/samples/petclinic/owner)
- The Kotlin Petclinic variant uses the same domain-feature vocabulary (`owner`, `vet`, `visit`) and also has `model` and `system` packages. — [Kotlin Petclinic package tree](https://api.github.com/repos/spring-petclinic/spring-petclinic-kotlin/contents/src/main/kotlin/org/springframework/samples/petclinic)
- Micronaut Petclinic documents a technical-layer vocabulary: `model` for data entities, `repository` for data-access interfaces, `service` for business logic, `dto` for form objects, `controller` for HTTP endpoints, and `system` for system concerns. — [Micronaut Petclinic README: Project Structure](https://github.com/micronaut-projects/micronaut-petclinic#project-structure)
- The maintained jMolecules examples repository contains both domain-oriented Spring Data examples and a presentation project with `customer` and `order` packages beneath the application package. The Spring Data JDBC example includes `Application.java`, `customer/CustomerManagement.java`, `customer/Customers.java`, and corresponding `order` types, demonstrating domain package names while retaining separate application/collection abstractions. — [jMolecules examples repository tree](https://api.github.com/repos/xmolecules/jmolecules-examples/git/trees/main?recursive=1)
- Spring Boot’s official layout example uses domain package names (`customer`, `order`) and puts controller, service, and repository types inside each domain package. It does not prescribe separate `domain`, `application`, `ports`, or `adapters` folders. — [Spring Boot: Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html)

### Inferences

- `owner`, `order`, `customer`, and similar capability names communicate the business boundary first. `controller`, `service`, and `repository` communicate technical roles first. The former is better aligned with Modulith-style module boundaries; the latter is common in framework sample applications.
- `spi` is a particularly precise name when the concern is an exposed contract inside a module. It says less about direction than `inbound` or `outbound`, but it gives Modulith a concrete visibility boundary and an allow-list token.
- The jMolecules examples suggest that a project can use domain packages and still distinguish application behavior (`CustomerManagement`) from persistence-facing abstractions (`Customers`) without introducing a universal `ports` folder. The source tree alone does not prove that every such type is a hexagonal port, so that interpretation should remain qualified.

### Gaps

- The jMolecules recursive tree establishes names and locations, but not the complete dependency direction. A source-file inspection of each example would be needed before classifying `Customers` or `CustomerManagement` as inbound or outbound ports.
- The Spring Modulith reference describes APIs and named interfaces rather than prescribing a universal folder name for adapters. It therefore cannot establish that `adapters` is preferred over `infrastructure`, `integration`, or a feature-specific package.

## 3. Comparative pattern matrix

### Takeaway

The strongest common pattern is not a particular folder name. It is a stable outer bootstrap, business-oriented module/package boundaries, constructor-injected collaborators, and a deliberate mechanism for selecting or restricting concrete implementations. The more explicit the architectural boundary, the more likely the code uses configuration, named interfaces, conditional implementations, or architecture verification in addition to ordinary framework scanning.

### Cited Findings

- **Spring Boot default:** root-package `@SpringBootApplication`; domain-named subpackages; scanning and auto-configuration assemble components; explicit `@Configuration`/`@Bean` is available when manual construction is needed. — [Spring Boot: Structuring Your Code](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html); [Spring Framework: @Bean and @Configuration](https://docs.spring.io/spring-framework/reference/core/beans/java/basic-concepts.html)
- **Canonical Spring Petclinic:** one thin launcher; feature packages; package-private MVC controllers; Spring Data repository interfaces; constructor injection; no visible application-wide wiring file in the representative tree. — [PetClinicApplication.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/PetClinicApplication.java); [OwnerController.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/owner/OwnerController.java); [OwnerRepository.java](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/owner/OwnerRepository.java)
- **Kotlin Spring Petclinic:** same Spring Boot composition style and domain package vocabulary, expressed with Kotlin’s `runApplication` entry point. — [PetClinicApplication.kt](https://github.com/spring-petclinic/spring-petclinic-kotlin/blob/main/src/main/kotlin/org/springframework/samples/petclinic/PetClinicApplication.kt); [Kotlin Petclinic README](https://github.com/spring-petclinic/spring-petclinic-kotlin)
- **Micronaut Petclinic:** thin `Micronaut.run` launcher; technical-layer folders; constructor/annotation-based bean discovery; environment conditions can select one concrete implementation of an interface. — [Application.java](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/Application.java); [Micronaut Petclinic README](https://github.com/micronaut-projects/micronaut-petclinic#project-structure); [StaticPetCareEmbeddingService.java](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/service/StaticPetCareEmbeddingService.java)
- **Spring Modulith:** direct subpackages are modules by default; root package is the module API; subpackages are internal; named interfaces and explicit dependency declarations narrow what other modules can use; verification checks cycles and illegal access. — [Spring Modulith: Fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html); [Spring Modulith: Verification](https://docs.spring.io/spring-modulith/reference/verification.html)
- **jMolecules examples:** domain-oriented `customer` and `order` packages recur in Spring Data examples and presentation material, while jMolecules/ArchUnit integration supplies a way to make architectural roles machine-verifiable. — [jMolecules examples repository](https://github.com/xmolecules/jmolecules-examples); [Spring Modulith verification and jMolecules integration](https://docs.spring.io/spring-modulith/reference/verification.html)

### Inferences

- **Most common assembly location:** the application package’s bootstrap class plus framework annotations, not a folder named `composition-root`. In explicit designs, look for `@Configuration`, `@Bean`, environment/condition annotations, or a module-specific configuration class.
- **Most common module location:** direct subpackages named after business capabilities. Technical folders are common in smaller or framework-centric samples, but they make module boundaries less obvious when one feature’s controller, service, and repository are spread across global folders.
- **Most useful contract names:** module root API, `spi`, or feature-specific interfaces. `ports` is clear when the project has consciously adopted hexagonal terminology; it should not be inferred merely because an interface exists.
- **Most useful adapter names:** concrete technology names or roles such as `StaticPetCareEmbeddingService`, `OwnerRepository`, or a configuration-created implementation. `adapter` is an architectural label, not a universal convention in Spring or Micronaut repositories.
- **Comparison in one sentence:** Spring Boot/Petclinic optimize for convention and low ceremony; Micronaut Petclinic adds explicit conditional implementation selection while retaining technical folders; Spring Modulith optimizes for verifiable business modules and controlled visibility; jMolecules provides annotations and verification that can make domain/hexagonal intent executable.

### Gaps

- No primary source examined here establishes a universal JVM convention for the exact folder name `composition-root`, `application`, `ports`, or `adapters`; the evidence supports several legitimate naming families instead.
- These repositories are examples and framework projects, not a statistically representative sample of all mature Java/Kotlin systems. The notes compare observed patterns and official guidance rather than ranking one layout as universally superior.
