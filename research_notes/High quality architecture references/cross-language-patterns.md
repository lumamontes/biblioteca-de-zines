# Cross-Language Patterns for Composition Roots and Ports/Adapters

## What underlying role do the names describe?

### Takeaway

The names are labels for responsibilities, not interchangeable architecture layers. The recurring boundary is an outer program that selects concrete technologies, constructs the object graph, and starts execution around an inner application/use-case model. Ports describe purposeful application conversations; adapters translate technologies to those ports. Configuration supplies values and environment choices, while entrypoints expose a runnable process.

### Cited Findings

- Cockburn's original ports-and-adapters description places the application inside, communicating through ports with external agencies; adapters translate technology-specific signals to the port's application API and back again. The pattern is intended to keep the application usable without a UI or database. — [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- Cockburn distinguishes primary/driving adapters, which activate an application, from secondary/driven adapters, which the application calls for data or notifications. The distinction is about who controls the conversation, not about a mandatory directory naming scheme. — [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- Cockburn says ports should be organized by purpose rather than technology, with multiple technologies implemented as interchangeable adapters for the same purposeful conversation. — [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- Microsoft's .NET guidance says services are normally registered at application start-up, then a service provider/host is built and run. Its example explicitly separates creating the host builder, registering services, building the host, and running it. — [Microsoft Learn, Dependency injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection)
- The Python architecture book calls its `bootstrap.py` a composition root and assigns it dependency injection plus other one-time initialization. It lists four responsibilities: declare defaults with overrides, perform startup work, inject dependencies, and return a configured core object. — [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc)
- The same Python source explicitly says entrypoints such as Flask and Redis should call the bootstrapper rather than each duplicating initialization and dependency construction. — [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc)
- The Cosmic Python project structure uses `entrypoints` for a Flask application, `adapters` for ORM/repository code, `service_layer` for application orchestration, and `config.py` for environment-derived settings. It warns against turning the config module into a general-purpose dumping ground. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc)

### Inferences

- `composition root`, `bootstrap`, and `wiring` are synonyms only when they refer to the same responsibility: the narrow outer location where concrete implementations are selected and assembled. `bootstrap` additionally suggests startup lifecycle work; `wiring` emphasizes connections; `composition root` emphasizes the architectural boundary. This distinction is an inference from the explicit bootstrap responsibilities and .NET host sequence. — [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc); [Microsoft Learn, Dependency injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection)
- `configuration` should not be used as a synonym for the whole composition root when it only reads environment variables or files. It may feed the root, but selection and construction of adapters are separate concerns in the cited Python example. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc); [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc)
- `application` most usefully names the inside boundary and its use cases, not the process launcher. Cockburn says use cases belong at the inner application boundary and should avoid intimate knowledge of outside technologies. — [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)

### Gaps

- No primary source found establishes a universal vocabulary or a required directory layout for these responsibilities. The sources consistently describe roles and dependency direction, while allowing project-specific names.

## How do .NET, Python, Rust, and TypeScript projects label the roles?

### Takeaway

Language ecosystems expose the same boundary through different conventions. .NET commonly makes host construction and service registration explicit; Python examples use `bootstrap.py`, `entrypoints`, `adapters`, and `config.py`; Rust commonly puts process startup in a binary crate or `src/bin/*` and delegates application behavior to a library; TypeScript frameworks commonly call the executable startup function `bootstrap` and use a module object as the registration/composition unit.

### Cited Findings

- In .NET, `Host.CreateApplicationBuilder(args)` creates the host builder, `builder.Services.Add...` registers concrete services against abstractions, `builder.Build()` creates the host, and `host.Run()` starts it. Microsoft's explanation says the host contains the DI service provider and other services needed to instantiate the worker. — [Microsoft Learn, Dependency injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection)
- The Microsoft eShop sample uses a separate `src/eShop.AppHost` project selected by `aspire.config.json`; its README describes that AppHost as the startup project and says `aspire run` starts the application model. This is a concrete .NET use of `AppHost` for process/resource orchestration rather than domain use cases. — [dotnet/eShop README](https://github.com/dotnet/eShop/blob/main/README.md)
- The Ardalis .NET template distinguishes Core, Use Cases, Infrastructure, and Web projects in its design-decision documentation index, and describes Clean Architecture as dependency-inverted architecture also known as hexagonal or ports-and-adapters architecture. — [ardalis/CleanArchitecture README](https://github.com/ardalis/CleanArchitecture/blob/main/README.md)
- Cosmic Python's example names the composition module `bootstrap.py`, the HTTP process module `entrypoints/flask_app.py`, technology implementations `adapters`, and environment access `config.py`. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc)
- In the Rust Tokio mini-redis project, `src/bin/server.rs` is documented as the server entry point. It parses command-line arguments, configures logging, binds a TCP listener, and passes the listener and shutdown signal to `mini_redis::server::run`; the server implementation lives in the library. — [tokio-rs/mini-redis, `src/bin/server.rs`](https://github.com/tokio-rs/mini-redis/blob/master/src/bin/server.rs)
- The Rust Book's workspace example has a binary package (`adder`) depending on library packages (`add_one` and `add_two`), and says the binary provides the main functionality while the libraries provide reusable functions. Cargo runs the binary through `adder/src/main.rs`. — [The Rust Programming Language, Cargo Workspaces](https://doc.rust-lang.org/book/ch14-03-cargo-workspaces.html)
- Rustlings' `src/main.rs` is a process-level entrypoint: it parses CLI arguments, performs initialization and state loading, then dispatches commands to modules such as `init`, `run`, `watch`, and `cmd`. The module named `cmd` is command behavior, not necessarily the composition root itself. — [rust-lang/rustlings, `src/main.rs`](https://github.com/rust-lang/rustlings/blob/main/src/main.rs)
- Nest's TypeScript starter calls its startup function `bootstrap`. The function creates the application from `AppModule` and listens on a port; `AppModule` declares imports, controllers, and providers, including configuration for an observability module. — [NestJS first steps](https://docs.nestjs.com/first-steps); [Nest TypeScript starter, `src/main.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/main.ts); [Nest TypeScript starter, `src/app.module.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/app.module.ts)
- A TypeScript architecture-testing project calls its layers `fluentapi`, `extraction`, `projection`, `assertion`, `error`, and `util`; its README explains each layer by behavior and dependency responsibility rather than by a generic `application` or `infrastructure` name. — [ts-arch/ts-arch, ARCHITECTURE.md](https://github.com/ts-arch/ts-arch/blob/main/ARCHITECTURE.md)

### Inferences

- `entrypoints` and `src/bin` primarily answer "which executable or delivery mechanism starts this use case?" They can perform boundary translation and lightweight startup, but the cited Rust and Python examples keep reusable application behavior elsewhere. — [tokio-rs/mini-redis, `src/bin/server.rs`](https://github.com/tokio-rs/mini-redis/blob/master/src/bin/server.rs); [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc)
- `AppHost` and `bootstrap` often include lifecycle/resource concerns that are broader than dependency registration. The .NET AppHost selects and launches a distributed application model, while Nest's bootstrap creates and listens on the framework application. — [dotnet/eShop README](https://github.com/dotnet/eShop/blob/main/README.md); [Nest TypeScript starter, `src/main.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/main.ts)
- `cmd` is ambiguous across ecosystems. In Rustlings it is a feature/module area for CLI commands; in many Go repositories it conventionally names executable packages. The Rust primary source supports the first claim, but this research did not establish a cross-language standard for the second.

### Gaps

- Frameworks can collapse composition into convention or decorators. The Nest starter demonstrates module metadata as registration, but does not define a general ports-and-adapters architecture.
- The examined Rust sources show executable/library separation but do not prescribe names such as `composition`, `bootstrap`, or `infrastructure`.

## What naming guidance is defensible across languages?

### Takeaway

Choose the name that tells readers what can be found there, and preserve the responsibility boundary even when the ecosystem uses another word. A compact cross-language vocabulary is: `application` for use cases and inner orchestration, `ports` for application-owned contracts, `adapters` or `infrastructure` for concrete external technology, `configuration` for values and environment decoding, `composition`/`bootstrap`/`wiring` for object-graph assembly and startup, and `entrypoints`/`cmd`/`src/bin` for executable surfaces.

### Cited Findings

- The original pattern's stable concept is dependency direction and purposeful conversations, not the word `hexagon` or a prescribed number of layers. Cockburn explicitly says the number of ports is a matter of taste and that the architecture focuses on inside/outside asymmetry. — [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- The Python source provides a strong naming test: the bootstrap script has one place for startup initialization, defaults, dependency injection, and returning the configured core object; entrypoints then call it. — [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc)
- The Python project structure provides a second naming test: configuration is centralized but deliberately kept narrow; adapters contain infrastructure code; entrypoints contain framework-facing launch code. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc)
- Microsoft's host example provides a lifecycle test: registration happens before build, and execution happens after build. A name such as `composition` or `bootstrap` is misleading if it hides runtime business behavior rather than setup. — [Microsoft Learn, Dependency injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection)
- The Rust mini-redis entrypoint provides a boundary test: command-line parsing, logging setup, binding, and shutdown wiring stay at the executable edge, while the reusable server logic is called from the library. — [tokio-rs/mini-redis, `src/bin/server.rs`](https://github.com/tokio-rs/mini-redis/blob/master/src/bin/server.rs)
- The Nest starter provides a framework-specific variant: `main.ts` performs framework application creation and listening, while `AppModule` declares providers and imports. These are composition responsibilities expressed through framework-native names. — [Nest TypeScript starter, `src/main.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/main.ts); [Nest TypeScript starter, `src/app.module.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/app.module.ts)

### Inferences

- The most reliable naming rule is behavioral: call a unit `configuration` if it reads/validates settings; `composition` or `bootstrap` if it constructs and connects concrete collaborators; `entrypoint` if it is selected by a runtime or CLI as the process boundary; and `infrastructure`/`adapter` if it implements an external protocol or persistence mechanism. This follows the responsibilities documented across the sources rather than any one ecosystem convention. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc); [Microsoft Learn, Dependency injection in .NET](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection); [Cockburn, Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)
- `application` and `infrastructure` should be treated as architectural roles, while `bootstrap`, `entrypoints`, `cmd`, and `src/bin` are often delivery or lifecycle roles. Mixing the two dimensions in one directory name makes it harder to tell whether a file defines policy, adapts technology, or starts a process. This is an inference supported by the contrasting Python, Rust, and .NET trees. — [Cosmic Python, Project Structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc); [tokio-rs/mini-redis, `src/bin/server.rs`](https://github.com/tokio-rs/mini-redis/blob/master/src/bin/server.rs); [ardalis/CleanArchitecture README](https://github.com/ardalis/CleanArchitecture/blob/main/README.md)
- There is no evidence that one preferred noun is universally superior. `bootstrap` is especially readable when startup initialization is part of the job; `composition root` is more precise when explaining dependency inversion; `wiring` is concise when the file mostly connects known objects; and `AppHost` or framework module names are appropriate when the framework owns the lifecycle. — [Cosmic Python, Dependency Injection and Bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc); [dotnet/eShop README](https://github.com/dotnet/eShop/blob/main/README.md); [Nest TypeScript starter, `src/main.ts`](https://github.com/nestjs/typescript-starter/blob/master/src/main.ts)

### Gaps

- These references do not provide empirical evidence that a particular name improves maintenance, onboarding, or defect rates. The recommendation is semantic and comparative, not a measured naming standard.
- The term `infrastructure` is broader than `adapter` in some .NET templates and may include deployment/resource concerns. The examined sources establish the name's use but not one universal scope, so a project should define it explicitly if it uses the term.
