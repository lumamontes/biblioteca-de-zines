# Keep Wiring Near the Process Edge

Across the surveyed Java/Spring/Kotlin, Go, .NET, Python, Rust, and TypeScript projects, composition roots are usually placed at the executable or framework bootstrap boundary, while application behavior and technology implementations remain elsewhere. **There is no cross-language standard folder named `composition-root`, `wiring`, or `bootstrap`.** Mature projects instead make the responsibility visible through a thin launcher, a framework module, an application assembly package, or an explicit bootstrap function. For Biblioteca de Zines, the best fit is to keep `src/application` for use cases, `src/infrastructure` for concrete adapters, and `src/composition/server` for explicit object-graph construction, with `app/**/actions.ts` and `scripts/**` acting as thin delivery entrypoints. This preserves the repository's existing pragmatic boundaries without introducing a full ports-and-adapters ceremony.

## Frameworks hide wiring, but explicit choices belong in configuration

Spring Boot and Kotlin Spring applications commonly use a root-package launcher whose annotations trigger component scanning; Petclinic's launcher is intentionally tiny, and its domain packages contain controllers, repositories, and models rather than a global wiring directory ([Spring Boot structuring](https://docs.spring.io/spring-boot/reference/using/structuring-your-code.html); [Java Petclinic launcher](https://github.com/spring-projects/spring-petclinic/blob/main/src/main/java/org/springframework/samples/petclinic/PetClinicApplication.java); [Kotlin Petclinic launcher](https://github.com/spring-petclinic/spring-petclinic-kotlin/blob/main/src/main/kotlin/org/springframework/samples/petclinic/PetClinicApplication.kt)). When implementation selection must be visible, Spring's recognized location is `@Configuration` with `@Bean`, not necessarily a composition-root package ([Spring `@Bean` and `@Configuration`](https://docs.spring.io/spring-framework/reference/core/beans/java/basic-concepts.html)). Micronaut similarly keeps a thin launcher but uses annotations and environment conditions to select implementations ([Micronaut Petclinic](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/Application.java); [conditional service](https://github.com/micronaut-projects/micronaut-petclinic/blob/main/src/main/java/io/micronaut/samples/petclinic/service/StaticPetCareEmbeddingService.java)).

The JVM evidence also shows that **business capability names such as `owner`, `order`, and `customer` are more common module boundaries than universal `ports` and `adapters` folders**. Spring Modulith formalizes this pattern: direct subpackages become application modules, their root package is the API, and internal subpackages are hidden; named interfaces such as `spi` can narrow the exposed contract ([Spring Modulith fundamentals](https://docs.spring.io/spring-modulith/reference/fundamentals.html); [named interfaces](https://docs.spring.io/spring-modulith/reference/fundamentals.html#modules.named-interfaces)). The implication is not to avoid explicit layering, but to name it only where it communicates a real boundary.

## Go keeps the graph beside the executable

Go projects make the composition boundary more explicit because the language has no built-in container. Go kit recommends constructing the complete graph in `func main`, passing dependencies through constructors, and keeping lifecycle setup there; its sequence visibly builds the service, middleware, endpoints, transport, and listener ([Go kit dependency injection](https://gokit.io/faq/#dependency-injection-mdash-why-is-func-main-always-so-big); [stringsvc example](https://gokit.io/examples/stringsvc.html)). Larger systems move that responsibility into an application package: Kubernetes uses `cmd/kube-apiserver/app` for staged configuration and server-chain construction, while Grafana separates command startup, bootstrap orchestration, and generated Wire providers under `pkg/server/bootstrap/wire` ([Kubernetes API-server app](https://github.com/kubernetes/kubernetes/blob/master/cmd/kube-apiserver/app/server.go); [Grafana bootstrap](https://github.com/grafana/grafana/blob/main/pkg/server/bootstrap/bootstrap.go); [Grafana Wire graph](https://github.com/grafana/grafana/blob/main/pkg/server/bootstrap/wire/wire_gen.go)).

The stable Go pattern is therefore **explicit constructors at a process boundary, with interfaces located near the consuming capability and concrete implementations in focused technical packages**. `cmd`, `internal`, `app`, `bootstrap`, and `wire` describe placement or mechanics, not a mandatory architecture. Go's own guidance favors meaningful package names and `internal` for server-only implementation rather than prescribing one layout ([Go module layout](https://go.dev/doc/modules/layout); [organizing Go code](https://go.dev/blog/organizing-go-code)).

## Other ecosystems separate startup, contracts, and technology

.NET makes registration and lifecycle explicit in the host sequence: create the builder, register services, build the provider, then run the host ([Microsoft dependency injection](https://learn.microsoft.com/en-us/dotnet/core/extensions/dependency-injection)). Python's Cosmic Python names the equivalent unit `bootstrap.py`; it declares defaults, performs one-time startup, injects dependencies, and returns a configured core object, while `entrypoints` call it and `adapters` hold technology implementations ([Cosmic Python bootstrapping](https://github.com/cosmicpython/book/blob/master/chapter_13_dependency_injection.asciidoc); [Cosmic Python project structure](https://github.com/cosmicpython/book/blob/master/appendix_project_structure.asciidoc)). Rust commonly puts process setup in `src/bin/server.rs` or `main.rs` and keeps reusable behavior in a library ([Tokio mini-redis server entrypoint](https://github.com/tokio-rs/mini-redis/blob/master/src/bin/server.rs)). NestJS uses framework-native names: `main.ts` is `bootstrap`, while `AppModule` declares imports, controllers, and providers ([Nest first steps](https://docs.nestjs.com/first-steps); [Nest starter](https://github.com/nestjs/typescript-starter/blob/master/src/app.module.ts)).

These examples support a precise naming test: use `configuration` for reading and validating settings, `composition` or `wiring` for constructing and connecting concrete collaborators, `bootstrap` when startup lifecycle is included, `entrypoint` for the process-facing adapter, and `infrastructure` or `adapter` for external technology. The terms are related but not interchangeable. Cockburn's original formulation reinforces that ports are purposeful application conversations and adapters translate external technology; it does not prescribe directory names ([Hexagonal Architecture](https://alistair.cockburn.us/hexagonal-architecture/)).

## Biblioteca should keep its existing three-way split

The repository should retain `src/application` for use cases and orchestration, `src/infrastructure` for Supabase, storage, source acquisition, rendering, and other concrete implementations, and `src/composition/server` for factories that assemble those implementations. This is the closest match to the evidence and to the repository's current structure: more explicit than Spring's convention-driven scanning, but smaller and less ceremonial than a global `ports`/`adapters` taxonomy. `app/**/actions.ts` should remain a thin framework adapter that creates or obtains the composition, invokes an application service, and revalidates paths; `scripts/**` should do the same for CLI processes. Configuration modules should supply validated values, not become an unbounded service locator or wiring dump.

The main tradeoff is discoverability versus ceremony. A dedicated composition boundary makes implementation choices, test seams, and environment-specific variants easy to inspect, but every new workflow can acquire a factory that framework-managed projects would avoid. Distributed framework wiring is shorter and idiomatic, but it hides the graph and makes replacement or isolated testing harder. The pragmatic threshold is to add or extend composition code when a workflow selects multiple concrete collaborators, has meaningful lifecycle or environment choices, or needs a test-specific graph; keep trivial framework-created dependencies in their existing feature or infrastructure modules. Do not add `ports` or `adapters` directories merely to rename interfaces whose ownership and direction are already clear.

## Conclusion

The strongest cross-language pattern is a **small, outer composition boundary with explicit construction, surrounded by inner application policy and outer technology adapters**. The noun varies by ecosystem, but the placement rule is stable: composition belongs near the executable or framework edge, not inside domain policy or low-level infrastructure.

Biblioteca already has the right shape. Treat `src/composition/server` as the repository's composition root, keep its factories thin and concrete, and let `src/application` and `src/infrastructure` remain the durable architectural vocabulary. This gives the project explicit dependency wiring where it matters without paying for a larger architecture than its workflows require.
